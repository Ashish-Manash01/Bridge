# Deployment

BRIDGE needs **one always-on web service that supports WebSockets** and a **PostgreSQL** database. The Docker image serves the API, the WebSocket endpoint and the web app from one origin, so HTTPS and WSS just work behind any host's TLS.

**Recommended:** Render (Docker web service) + Supabase (PostgreSQL). Roughly $7/month (Render Starter) + $0 (Supabase free tier) for a pilot.

> Vercel/Netlify alone won't work: their serverless functions don't keep WebSocket connections open. You can host the web app there, but the API must run on a WebSocket-capable host (option C).

---

## 0. Before you start

- [ ] A GitHub account (to connect the host to your code)
- [ ] A long random `SECRET_KEY`: `python -c "import secrets; print(secrets.token_urlsafe(48))"`
- [ ] Optional: `SARVAM_API_KEY` for server speech/voice in Indian languages; `MYMEMORY_CONTACT_EMAIL` to raise the free translation quota
- [ ] Optional: a domain name

### Push the code to GitHub

```bash
cd Bridge
git init
git add .
git commit -m "BRIDGE initial release"
# create an empty private repo on github.com, then:
git remote add origin https://github.com/<you>/bridge.git
git branch -M main
git push -u origin main
```

`.gitignore` already excludes `.env`, databases, certificates, `node_modules` and virtualenvs. Double-check `git status` shows no `.env` before pushing.

## 1. Database: Supabase

1. supabase.com → **New project** → choose a region close to your users (e.g. Mumbai `ap-south-1`) → set a database password.
2. **Project Settings → Database → Connection string → URI**. Use the **Session pooler** string (IPv4-friendly), port 5432:
   `postgresql://postgres.<ref>:<password>@aws-0-ap-south-1.pooler.supabase.com:5432/postgres`
3. That's your `DATABASE_URL`. BRIDGE converts `postgresql://` to the async driver automatically and is pooler-compatible.
4. Migrations run automatically on every deploy (`alembic upgrade head` in the container start command).

Backups: Supabase free tier keeps daily backups for 7 days; Pro adds point-in-time recovery. To delete everything: `DELETE FROM rooms;` cascades to participants, utterances, translations, feedback, glossary and summaries.

## 2A. App: Render (recommended)

1. render.com → **New → Blueprint** → select your GitHub repo. Render reads `render.yaml` and creates the `bridge` web service (Docker, Starter plan, health check `/api/health`).
2. Fill the prompted environment variables:

   | Key | Value |
   |---|---|
   | `DATABASE_URL` | Supabase URI from step 1 |
   | `CORS_ORIGINS` | `https://bridge-xxxx.onrender.com` (your Render URL; add your custom domain later) |
   | `SECRET_KEY` | auto-generated by the blueprint |
   | `SARVAM_API_KEY`, `MYMEMORY_CONTACT_EMAIL` | optional |

3. **Deploy**. The first build takes ~5 minutes. Open `https://<your-app>.onrender.com/api/health`; it should show `{"status":"ok","database":true}`.
4. Open the site on two phones, create a room, scan the QR code, and run the manual checklist in `docs/testing.md`.

Custom domain: Render → Settings → Custom Domains → add `bridge.yourdomain.com`, create the CNAME it shows at your DNS provider. HTTPS certificates are automatic. Then add the domain to `CORS_ORIGINS`.

## 2B. App: Railway or Fly.io (alternatives)

**Railway:** New Project → Deploy from GitHub repo (detects the `Dockerfile`) → Variables: same as above, plus `PORT` is provided automatically → Settings → Networking → Generate Domain.

**Fly.io:**
```bash
fly launch --no-deploy          # detects the Dockerfile; pick region bom (Mumbai)
fly secrets set SECRET_KEY=... DATABASE_URL=... CORS_ORIGINS=https://<app>.fly.dev
fly deploy
```
Keep at least one machine running (`min_machines_running = 1`) so WebSockets aren't cut by scale-to-zero.

## 2C. Split hosting (web on Vercel, API elsewhere)

1. Deploy the API as in 2A/2B (it still works without the web app).
2. Vercel → Import repo → Root directory `apps/web` → Framework Next.js → env vars:
   `NEXT_PUBLIC_API_URL=https://api.yourdomain.com`, `NEXT_PUBLIC_WEB_URL=https://yourdomain.com` → Deploy.
3. Set the API's `CORS_ORIGINS=https://yourdomain.com`.

## 3. Switching to production providers (when you have keys)

Set env vars on the host and redeploy; no code changes:

```
STT_PROVIDER=sarvam
TRANSLATION_PROVIDER=sarvam
TRANSLATION_FALLBACK_PROVIDER=mymemory
TTS_PROVIDER=sarvam
SARVAM_API_KEY=...
SARVAM_TRANSLATE_MODE=formal        # optional; default
SARVAM_TTS_MODEL=bulbul:v3          # optional; default (v2 is retired)
```

Then run the evaluation from your machine against the same config (`python -m scripts.evaluate_providers` with the keys in `.env`) and commit the updated `app/core/evaluation_results.json`.

## 4. Staging vs production

Create a second Render service (or Railway environment) named `bridge-staging` from the same repo, with its **own** Supabase project and `BRIDGE_ENV=staging`. Test there first (including the e2e suite: `E2E_BASE_URL=https://bridge-staging.onrender.com npm run test:e2e`), then promote.

## 5. Operations checklist

- [ ] `/api/health` monitored (Render does this; add UptimeRobot for alerts)
- [ ] Logs: Render → Logs (structured JSON, no message content)
- [ ] Cost: `usage_records` table holds provider usage and estimated cost per room
- [ ] Limits tuned in env (`MAX_PARTICIPANTS_PER_ROOM`, `MAX_AUDIO_SECONDS_PER_ROOM`, rate limits)
- [ ] Run a single instance (in-process realtime hub). For multiple instances see `docs/architecture.md#scaling-notes`
- [ ] Privacy policy published before public launch (`docs/privacy.md`)
- [ ] Provider data-retention terms reviewed
